# Architecture

Hermes Native is one GTK 4 / libadwaita process. The window is a sidebar plus a transcript plus a composer. Nothing here installs a package, a desktop shortcut, or a settings screen.

## Window

The sidebar lists server session metadata, offers **New conversation** (`Ctrl+N`), and triages sessions locally into **All**, **Chats** (interactive sources such as `tui`, `local`, `api_server`, and messaging channels), **Auto** (automated `cron`, `heartbeat`, `webhook`, `kanban`, and background runs), and **Pinned** (`★`) with fuzzy local filtering plus live debounced server-wide FTS5 search (`Ctrl+F`). Pinned conversations float to the top of both the sidebar and Command Palette with a **`★ PIN`** badge. Rows show the server title, cleaned 1-line conversation preview, semantic source badge, message count, compact model badge, relative age, and a read-only mark when resume is refused. Hover never selects or resumes a row. Live `session.title` WebSocket broadcasts update the open header and sidebar row in place. Deleting the open conversation prompts for destructive confirmation (`AdwAlertDialog`) before sending `session.delete` and resets the window to the launch state on completion.

The header bar provides an **Omnisearch** (`Ctrl+K`) Command Palette (`AdwDialog`) for keyboard-first navigation on Hyprland: instant local fuzzy-jumping, live debounced full-server SQLite FTS5 search across thousands of remote conversations, and contextual actions (new chat, switch/launch in remote workspace `Ctrl+Shift+W`, attach files `Ctrl+U`, compress context `/compress`, find in transcript `Ctrl+Shift+F`, pin/unpin `Ctrl+P`, rename `F2`, archive `Ctrl+Shift+E`, model picker `Ctrl+M`, Flight Deck `Ctrl+I`, sidebar toggle `Ctrl+B`, filter focus `Ctrl+F`, triage switches, history reload `Ctrl+R`, pagination, reconnect, and delete).

## Composer Studio (Workspace Launch, `/` Skills Deck, Native Wayland Vision & Context Compaction)

- **Workspace-Scoped Launch & Picker (`GET /api/chat/workspaces` + `session.create` `cwd`)** — a searchable `WorkspacePicker` pill in the composer (`Ctrl+Shift+W`, `/workspace [query]`, or Command Palette) lists remote git repositories and project directories alongside the server's `default_cwd`. Selecting a workspace scopes new chats (`session.create` `"cwd"`) directly to that remote repo so Hermes inherits its `AGENTS.md`, git branch, and working directory; picking a different workspace while inside an open chat launches a fresh conversation in that repo.
- **Floating `/` Command & Server-Skill Autocomplete Deck (`GET /api/skills`)** — typing `/` at the start of the composer reveals `SlashDeck` above the input (`↑`/`↓` navigate, `Tab` complete, `Enter` run zero-arg commands or complete skill/arg prefixes, `Esc` dismiss), combining client slash commands (`/btw`, `/compress`, `/attach`, `/workspace`, `/branch`, `/undo`, `/retry`, `/regen`, `/find`, `/pin`, `/rename`, `/archive`) with all enabled server skills ranked by fuzzy match and usage count.
- **Document context** — the attachment picker and drop target accept UTF-8 text and text-bearing PDFs as well as images. Files are read and PDF text extracted off the UI thread. Document text is included in the submitted prompt and therefore becomes server-side conversation history; the original document is not uploaded. Each input is limited to 15 MB and extracted text to 1 MB. Unsupported binary files, unreadable PDFs, and PDFs without extractable text are rejected; scanned PDFs require OCR before attaching. Up to six attachments can be staged per message.
- **Native Wayland Multimodal Image Staging (`POST /api/chat/image-upload` + `image.attach`)** — up to six PNG, JPEG, WebP, or GIF images (up to 15 MB each) can be staged in `AttachmentStrip` on either the Launch Screen or a live writable conversation via `Ctrl+V` Wayland screenshot paste (`GdkClipboard::read_texture_future`), drag-and-drop (`GtkDropTarget`), or `Ctrl+U` / **Attach** button / `/attach` (`GtkFileDialog`). Thumbnails render natively via `GdkTexture` + `GtkPicture`; on submit, `hermes-net` uploads staged images to `/api/chat/image-upload`, attaches each server path sequentially via `image.attach`, and dispatches `prompt.submit`.
- **One-Click & `/compress` Context Compaction (`session.compress`)** — idle conversations with two or more messages expose **`⚡ Compress`** in the Flight Deck **Trace** tab's `CONTEXT & TELEMETRY` card, `/compress` (`/compact`) in the composer, and **Compress conversation context** in the Command Palette. When compaction removes older messages, the backend re-syncs the session (`session.resume` + tail `GET /api/sessions/{id}/messages`) so message counts, token gauges, and transcript rows reflect the compacted history; when context is already small (`noop: true`), it settles cleanly in place.

## Deep Recall (FTS5 Omnisearch & In-Transcript Find) and Session Curation

- **Server-wide FTS5 Omnisearch (`GET /api/sessions/search`)** — typing two or more characters in **Omnisearch** (`Ctrl+K`) or the sidebar filter (`Ctrl+F`) runs instant local matching and, after a 180 ms debounce, queries the gateway's SQLite FTS5 index across all unarchived server conversations (beyond the 50-row local sidebar page). Server `>>>match<<<` markers are strictly XML-escaped before rendering Pango `<b>match</b>` snippet highlights, with secrets redacted. Selecting any FTS5 hit opens or resumes the conversation and hands the query directly to the **In-Transcript Find Bar**, scrolling straight to the matching message.
- **In-Transcript Find Bar (`Ctrl+Shift+F`, header search button, or `/find [query]`)** — opens a native search bar above the transcript with a live `k / N` match counter, `Enter` (next) / `Shift+Enter` (previous) / `Esc` (close) navigation, `.message-match` / `.message-match-active` card highlights and badges in `GtkListView`, and a one-click **Search earlier pages** button when `history_before > 0`.
- **Server-persisted Session Curation (`PATCH /api/sessions/{session_id}` + `/mutation-snapshot`)** — conversations can be **Pinned / Unpinned** (`Ctrl+P`, header star button, `/pin`), **Renamed** (`F2` or header edit button opening a compact `AdwDialog`, or `/rename <title>`), and **Archived** (`Ctrl+Shift+E`, Command Palette, or `/archive`, hiding the session from active `archived=exclude` lists without permanently deleting server data). Mutations fetch `GET /api/sessions/{id}/mutation-snapshot` to attach Hermes `0.23.1+` optimistic concurrency fencing (`request_id`, `expected_revision`, `expected_generation`) with automatic refresh retry on revision races, while staying compatible with older gateways. For newly created 0-turn sessions that have no SQLite row yet, pin/rename mutations apply optimistically and flush automatically once the first turn persists.

The **Flight Deck** (`Ctrl+I`, or the live context-budget badge on the right of the header bar) opens a collapsible inspector beside the transcript with three views:
- **Side-Ask (`/btw`)** — sends `prompt.btw` against a read-only snapshot of the active session (`Alt+Enter` or `/btw <question>` in the main composer, or directly inside the drawer) and renders `btw.complete` in Markdown with **Copy** and **↗ Insert into draft** promotion. Side questions work even while a turn streams or is stopping, never alter server history or turn alternation, and never fail or reopen an active turn if refused.
- **Live Trace** — displays session context-window occupancy, token/throughput/cost metrics (`session.usage`, `message.complete`, and `session.info`), the current turn's selectable reasoning stream (`reasoning.delta` / `thinking.delta`), and a live chronological tool timeline (`tool.start`, `tool.progress`, `tool.output_risk`, `tool.complete`).
- **Map (Outline)** — indexes user turns and assistant code-fence milestones so clicking any entry scrolls the virtualized `GtkListView` directly to that message, with a per-turn **`⑂`** action to fork a new conversation right after that turn.

## Non-linear branching, turn rewind, and lineage

Conversations are treated as navigable trees rather than append-only logs:
- **Point-in-time & whole-conversation branching** — any conversation with saved or streamed User/Assistant messages can be forked from the header bar (**Branch** / `Ctrl+D`), Command Palette (`Ctrl+K`), composer slash commands (`/branch [title]` or `/fork [title]`), Flight Deck Turn Map (`⑂`), per-message **`⑂ Branch`** pills, or the read-only banner's **`⑂ Fork into live chat`** button. Live sessions call `session.branch` (including server-wide `count` when forking mid-transcript across paginated histories); read-only or cold conversations call `session.branch_stored` and gracefully fall back to a seeded `session.create` (`parent_session_id` + visible transcript prefix) if the gateway refuses direct stored branching.
- **Live turn rewind (`session.undo`)** — idle writable sessions expose inline **`↺ Edit & retry`** on the latest user turn (rewinds the turn on the server and loads the prompt back into the composer for editing), **`↻ Regenerate`** on the latest assistant reply (rewinds and immediately re-submits for a fresh completion), and `/undo`, `/retry`, and `/regen` (`/regenerate`) slash commands plus Command Palette entries. After `session.undo` soft-archives the dropped SQLite rows, the backend refreshes the live session's authoritative `message_count` and tail history page before settling the UI.
- **Lineage navigation** — `GET /api/sessions` rows carry `parent_session_id`. Because the server collapses auto-compressed segments to a single tip row, Hermes Native marks **`⑂ FORK`** badges only on true forks (visible parent session, recorded branch, or `(branch)` suffix) and renders an interactive **Lineage Bar** above the transcript with one-click **`↖ Parent`** jump and a **`⑂ Branches · N`** popover menu for child forks.

The transcript is a `GtkListView`. GTK recycles the visible row widgets. Each conversation message uses native widgets from a per-block Markdown parse: headings, lists, links, code, and tables. Assistant text and tool-result notations are grouped in chronological order within a response card. Live tool starts show the gateway’s redacted context or argument preview when available, use an activity-specific icon, and update on completion; saved tool-result rows show the tool name when available, not their arguments or output. Prose and code are selectable. **Copy original message** copies the displayed message text (the summary for tool rows). **Copy code** copies that fence. Links open only after normalization, and only for `http`, `https`, and `mailto`. Other schemes stay inert. HTML is literal text. Images are alt text and are never fetched. There is no webview.

The composer is a multiline editor anchored at the bottom and focused on launch. Typing on the empty launch screen and pressing Enter creates a server-owned conversation titled from the opening prompt and dispatches the first turn once `session.create` confirms; if creation fails or disconnects, the launch draft stays intact and is never replayed. Inside an open conversation, Enter sends (or steers a running turn via `session.redirect`), Shift+Enter inserts a line, and Stop is available only while a turn is busy. Clarify and approval controls appear only when the server asks. Choices are the server’s list, with allow-once and deny as the approval fallback when the server sends no choices. An approval card is implemented; whether a live server shows one depends on that server’s policy. This document does not claim a live approval card has been observed.

## Model picker

The composer's bottom-left trigger names the model and its provider, and opens a popover with a search field over the server's configured catalog. Rows keep provider and model together: the same model name under two providers is two rows, and a row whose name cannot be sent to the gateway (whitespace, or a leading `-`) is shown as unavailable instead of being silently rewritten. Search is local: it never sends a request and never selects anything. Hover does not commit; a single click on a row or Enter inside the search field selects it. On the welcome screen, selecting a model creates a conversation, carries the draft and attachments into it, and waits for the model-switch response before allowing the first send. Enter in the picker never submits the draft, and Escape returns focus to the editor.

The catalog is fetched once per connection with `explicit_only: true`, `include_unconfigured: false`, and `refresh: false`, and is dropped when the connection closes so a reconnect cannot show another connection's rows.

A switch is `config.set` with `session_id`, `key: "model"`, and the value `<model> --provider <provider> --session`. `--session` is mandatory: without it the gateway may persist the choice as the profile default, and a reply whose `scope` is not `session` is treated as a refusal. A value with quoted tokens is rejected by the gateway's `split()` tokenizer, which is why unrepresentable catalog rows are disabled rather than quoted.

A chat that has never run has no agent yet. The client sends a provider-less prime first, then the scoped switch. That acknowledgement is not treated as proof: a repeat against this gateway has had the first inference report a different model. The trigger stays on "Switching to …" until the completion's `usage.model` arrives, and a different reported model replaces the selection. A chat that has already run switches directly, and a session-scoped acknowledgement confirms that pair.

A switch made while a turn streams is answered `deferred: true`. It applies from the next turn: the running turn keeps the model it started with, and the trigger says so. A deferred reply is the only queued state the client shows.

The displayed model is never inferred from the catalog. It comes from create and cold-resume metadata, or from the completion's `usage.model` for an inference that actually ran. A pending switch reads "Switching to …", a deferred one reads "… · next turn", and a request that never answered reads "unconfirmed" and is not retried. A definite refusal or a cancelled confirmation keeps the previous selection and the draft. When the gateway returns `confirm_required` the client asks explicitly and only then repeats the same target with `confirm_expensive_model: true`.

Lazy `model.options` is not used as evidence of a chat's effective model: for an uninitialized session it reports the profile default.

An interrupt acknowledgment means **Stopping**, not completion. Send remains blocked and Stop is disabled until the server's terminal event. Late text or submit acknowledgments cannot reopen a stopping turn. Late human requests and queued answers are cancelled rather than reopening controls or granting an action after Stop.

Drafts and the selected session stay in memory for the process lifetime, including across an explicit reconnect. They are not written to disk. Already loaded per-session histories stay in memory the same way. Quitting drops them. The next launch reloads from the server.

## Transport

`hermes-net` is a dedicated thread with a current-thread Tokio runtime. The UI thread only sends commands and drains events.

The dashboard gateway is used instead of the separate HTTP API server because the client must resume eligible existing CLI/TUI conversations, not only API-created chats.

Login is `POST /auth/password-login` with provider `basic` and a cookie jar. Each WebSocket open asks for a fresh single-use ticket (`POST /api/auth/ws-ticket`) and connects to `/api/ws?ticket=…`. TLS uses the default rustls verifier. Certificate checks are never disabled. Redirects stay on the same origin.

`stored_id` is the server’s durable conversation id. `runtime_id` identifies a live execution session; it is not the durable id and is not assumed to change with every socket. HTTP session metadata is paged newest-first in batches of 50. Saved message pages are internally chronological and use absolute oldest-first history offsets. The client keeps no authoritative local history database.

A refused resume (including RPC 4132, and a kanban source the client will not continue) loads the saved transcript as read-only. Refusal never silently forks a conversation; instead, the read-only banner offers an explicit **⑂ Fork into live chat** action (`Ctrl+D`) if the user chooses to continue from that transcript in a new writable branch.

Reconnect is the header button. It drops the socket and opens a new one. Pressing Reconnect while a sign-in is already in flight aborts that attempt (dropping its futures cancels the HTTP requests and socket dial) and retries immediately, instead of waiting out the 90s connect bound. Prompts are not replayed. Explicit server rejection is a failure; an interrupted socket write or mid-turn disconnect leaves the outcome unknown. Partial text may be incomplete; the client does not guess that the server finished or failed. Empty or unrecognized terminal statuses are also unknown.

An unintentional drop is retried automatically with exponential backoff: the first retry starts 0.5–1s after the loss (equal jitter — half the scheduled delay is fixed, half comes from wall-clock nanos) and the interval doubles to a 30s cap, resetting after a successful reconnect. The jitter desynchronizes clients: a gateway restart that drops many at once spreads each retry attempt across the second half of its scheduled delay instead of a lockstep herd. Each attempt's steps are bounded independently at their own latency class: the password login and ticket requests carry a 10s `SIGN_IN_TIMEOUT` and the WebSocket handshake (TCP + TLS + upgrade) a 10s `DIAL_TIMEOUT` — pure auth/transport round-trips that have not completed in that window are wedged or black-holed, so a reconnect cycle against a wedged endpoint runs three times faster instead of burning two full 30s RPC waits per try. Queued commands survive the retry cycle and drain once the gateway reports ready — but only the same allowlist in both not-ready and mid-dial states (list, create, resume, search, studio fetch), because those replay against fresh state; a Submit, Steer, Interrupt, or timeline action issued while a dial is in flight carries runtime ids from the torn-down connection, so it fails immediately with "Not connected. Reconnect to try again." rather than replaying against dead state. Authentication rejections (bad password, rate-limited login, rejected session) are never retried automatically; the header button remains the manual path.

Idle keepalive is protocol-level: after 30s without any inbound frame the client sends a WebSocket Ping (RFC 6455). A live gateway answers Pong, refreshing the liveness clock, so a healthy idle connection stays up instead of being dropped by the 90s inbound-silence bound. The socket is dropped only when a probe cannot be written or the gateway stays silent for 90s despite probes.

On `gateway.ready` the queued commands drain first, then the studio workspace and skill catalogs are fetched over HTTP concurrently. Queued user actions never wait on catalog round-trips, and the two catalog requests share one wall-clock window. The catalog fetch runs as its own task off the transport loop: a slow or stuck gateway HTTP endpoint cannot stall frame processing, probe answering, or command handling during the post-ready window (each HTTP call is bounded by the 30s RPC timeout; a reconnect simply spawns a fresh fetch that supersedes any stale one).

Streaming deltas never block the transport loop on UI speed: `MessageDelta` and reasoning stream events (`reasoning.delta` / `thinking.delta` / `reasoning.available`) ride a non-blocking send with per-runtime in-memory tails (capped at 1 MB), retried on every inbound frame — the UI gets a whole inter-frame gap to drain — with the 5s maintenance tick as the fallback when no frames flow (server-side compress). A parked reasoning tail replays the replace flag its live stream would have carried, resets wholesale on `reasoning.available`, and never leaks into the next turn's trace (a turn roll drops it). A slow UI therefore cannot stall ping/pong answering or command processing, the bounded event channel still protects memory, and a tail resumes within one frame once the UI catches up. `MessageComplete` carries the authoritative text, so a dropped tail degrades only live streaming display.

Delta frames are also the decode hot path: a `message.delta` frame parses straight into borrowed fields (`delta_frame_fields`, a zero-copy serde envelope) with no JSON DOM, and dispatches directly to the delta state machine — per-token frames cost one allocation-free scan plus the event's own strings instead of a full `Value` tree. Every other frame keeps its single full parse: a needle pre-filter guards the fast path, so tool outputs or history replies that merely mention the event name fall through to the envelope check and then the ordinary `Value` route, with routing unchanged. The events themselves carry `Arc<str>` runtime and message ids cloned from a pending-delta entry that survives successful sends, so a steady frame allocates exactly one buffer — the delta text — down from seven (map key, entry id, two event ids, tail, turn-id clone, and an unconditional id rewrite); a count-of-allocations regression test pins that budget.

On the UI side the render cost of a streamed chunk is one row, not the transcript: the 60ms event poll drains queued events and refreshes once per batch, and the model splits its revision counters — `stream_revision` moves only when a streaming append grows the trailing message in place, while `revision` (rows, gates, find state, completion) rebuilds the whole list as before. A stream-only change splices just the trailing transcript row (`trailing_row_update` rebuilds the folded assistant/tool run the full pass would produce), so per-batch work no longer clones and byte-compares every stored message on the way to the one row that changed.

Login-session expiry heals itself: every REST helper (session list, saved history, search, fenced patches, image uploads, workspace/skill catalogs) shares a per-task trip flag that an HTTP 401 sets, and the task reports `LoopWork::AuthRejected` through the work channel. The first report while a socket is live emits one disconnect event and tears the socket down — the regular reconnect cycle then re-runs password sign-in, refreshing the cookie, and the flag resets on that success; further rejections inside the same window are absorbed. An expired session is transient (retryable stays true), so a gateway restart or cookie TTL no longer wedges every user action until an app restart; only a genuinely rejected password marks the failure permanent, exactly as before.

Session reads (conversation list, saved history, session search) and session mutations (pin/rename patches, including the fenced-patch conflict retry) run off the transport loop as their own tasks. The history, search, and patch outcomes emit or re-enter directly; the list fetch re-enters the loop through a small internal work channel, where title/preview cleaning and the listing caches (message counts, pin state, refused sources) are applied before the event reaches the UI, and the patch outcome applies where curation state lives — the unpersisted-live guard is evaluated on the loop. A slow or stuck gateway HTTP endpoint therefore cannot stall frame processing on user-initiated reads or mutations either — including the post-reconnect refresh, whose list and history fetches used to block the loop up to 30s each.

Curation on an unpersisted conversation defers until its first message completes, then the saved title/pin patch runs off the loop like any other. The flush is serialized: a session has at most one patch in flight, a mutation pressed while one is running rides the deferral instead of racing the fenced revision, and a refused save re-defers the user's intent and surfaces — a rename or pin can no longer silently revert on the next list refresh. A transport failure re-defers quietly and retries on the next message; the gateway's refusal (404/409) reaches the user as a curation error.

Attachment uploads ride the same shape: `begin_submit` hands the staged images to a task that uploads them **concurrently** (`try_join_all`, so N images cost one wall-clock window instead of N serial round trips) and hands the paths back through the work channel, where the turn's generation guard discards results that arrive after the turn rolled, stopped, or the link reconnected. A slow or stuck upload therefore cannot stall frame processing on the message-send path.

Branching a conversation fetches its earlier visible pages the same way: `begin_branch` hands the page walk (up to ceil(before_loaded / PAGE) history round trips) to a task and applies the seeds on the loop when they arrive, so a slow history endpoint cannot stall frames while a branch is prepared. The branch-completion page (the new conversation's first rows, with the fallback seed riding on error or an empty page) and the archive patches (including the deferred fire-and-forget patch after a message completes) also run off the loop — a mechanical sweep of HTTP-helper call sites confirms no user-initiated HTTP call executes on the transport loop anywhere.

Every off-loop fetch is stamped with the connection epoch it was spawned on. `close_socket` bumps the epoch on every teardown — drop, reconnect, shutdown — and the work-channel dispatch in `run()` discards any result whose epoch no longer matches, so a fetch that started under one connection never applies state to the next: a resume page fetched before a drop cannot adopt a turn for a runtime the new connection never resumed, and stale branch, mutation, archive, and upload results are dropped rather than misapplied. Tasks carry the channel as a `WorkSink` bound to the live epoch, so a future task cannot forget the stamp — the plain sender type never reaches a task signature.

Socket writes never run on the transport loop. A background writer task owns the socket sink for the lifetime of one connection; the loop only enqueues frames (JSON-RPC requests, Pong replies, keepalive pings, the Close frame), which cannot block. The writer applies each frame in order inside a 5s `WRITE_TIMEOUT` — far below the 30s RPC response wait — and a write that cannot complete (TCP backpressure, half-open connection) reports a dead link through the work channel, so the loop tears the link down and reconnects exactly like any other socket loss. A wedged gateway therefore costs frame processing nothing: inbound deltas, events, and user actions keep flowing while the write failure is detected in the background, and in-flight jobs fail with the disconnect instead of waiting out their full RPC deadlines.

## Configuration

`main` loads `./.env` from the process working directory only. There is no parent-directory walk. Variables already set in the process are left as they are. Client configuration consumes only `HERMES_GATEWAY_URL`, `HERMES_USER`, and `HERMES_PASSWORD`. The URL must be an origin: no userinfo, path, query, or fragment. `HERMES_BASIC_AUTH_SECRET` is not consumed as client configuration, sent, or bundled.

`--trusted-tunnel` is the only behavioral flag. It allows `http` solely for loopback (`localhost`, IPv4 127.0.0.0/8, IPv6 loopback) and Tailscale (`*.ts.net`, 100.64.0.0/10, `fd7a:115c:a1e0::/48`). Other private addresses, including generic WireGuard ranges, stay rejected. Public HTTP is rejected. HTTPS does not need the flag.

No local Hermes process is required or contacted.

## Checks

Verification results, remote smoke details, and process RSS measurements: [implementation evidence](../.context/2026-11-08.hermes-native-client/verification-implementation.md). Run the project checks with:

```sh
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --all -- --check
```

Manual remote smoke, from the project directory, against the configured remote only:

```sh
cargo run --release --example remote_smoke -- --trusted-tunnel
```

The example always requires `--trusted-tunnel` as an explicit confirmation. It creates disposable chats, checks a two-turn context word against a second distinct chat, runs an ephemeral `prompt.btw` snapshot side question and verifies saved history stays untouched, forks a point-in-time branch (`session.branch` with `count: 2`), proves the branch inherits context on a new turn, rewinds that turn via `session.undo` and verifies the server row count drops back, reconnects, pins and renames a chat via `PATCH /api/sessions/{id}`, verifies full-text `GET /api/sessions/search` returns Pango-highlighted FTS5 snippets, archives a disposable chat and confirms active list exclusion, fetches remote workspaces (`GET /api/chat/workspaces`) and skills (`GET /api/skills`), launches a workspace-scoped session (`session.create` with `cwd`), uploads and attaches a real PNG image (`/api/chat/image-upload` + `image.attach`) on a live multimodal turn, runs `session.compress`, switches one new chat to a second configured model, checks that the first inference reported that model, checks the server default did not move, and deletes what it created. It must not be pointed at conversations you want to keep. If cleanup fails it prints `disposable-id` lines; those ids are the operator’s to close.

The deterministic contract lives in `guardrails.json` (v2); run it with `npm run guardrails:check`.

Build and launch steps: [Run Hermes Native](howto/run-hermes-native.md).
